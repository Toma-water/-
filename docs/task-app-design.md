# タスク管理アプリ 設計書

対象:自分専用のタスク管理・生活運用アプリ(Web / React想定。アプリ本体は別途実装)。
この設計書は「何を作るか」「なぜその形か」「毎日どう使うか」「AIをどう組み込むか」を定義する。

---

## 1. 解決したい問題と設計原則

### 1.1 困りごと → 原因の整理

挙げられた困りごとは多いが、原因はほぼ次の5つに集約できる。

| 原因 | 該当する困りごと |
|---|---|
| **A. 次の一手が決まっていない** | 起きた瞬間に何をすべきか分からない/何から始めるか決めるまでに時間が溶ける/短いタスクの後に迷う/明日の最初の一手が決まっていない |
| **B. タスクが抽象的で完了条件がない** | 「勉強する」「片付ける」で終わった感じがしない/「今日は勉強した」の基準が曖昧/何もしてない感 |
| **C. 崩れたときの復帰ルートがない** | 予定が崩れると全部どうでもよくなる/「今日は失敗した」の後に戻れない/YouTubeに流される |
| **D. 記録と振り返りが行動に変換されない** | 反省が次の行動にならない/進捗が見えない/何が積み上がっているか分からない/復習タイミングを忘れる |
| **E. 情報の置き場が分散している** | メモの場所を忘れる/Notion・紙・スマホに散らばる/決定事項が消える/保存資料を読み返さない |

### 1.2 設計原則

1. **常に「次の一手」が1つだけ表示されている状態を作る。** 選択肢を並べない。迷う余地を消す。
2. **完了条件のないタスクは登録できない。** 抽象タスクはAIが自動で具体化する。
3. **計画は崩れる前提で設計する。** 復帰は「ボタン1つ」でできること。
4. **効率性 = 成果 ÷ 時間。** すべてのタスクに「見積時間」と「成果ポイント」を持たせ、1日の効率を数値で見せる。
5. **入力の入口は1つ(Inbox)。** 仕分け・構造化はアプリ(とAI)の仕事であって、人間の仕事にしない。

## 3. データモデル

```typescript
// タスク:完了条件が必須。抽象的な入力はAIが分解してこの形にする
interface Task {
  id: string;
  title: string;              // 例:「数学の問題集 p.12–15 を解く」
  purpose?: string;           // なぜやるか(目的がない作業が苦手 → 一言でも意味づけを持たせる)
  doneCriteria: string;       // 完了条件。例:「4ページ解き終えて丸付けまで済んでいる」★必須
  firstStep: string;          // 最初の一手(2分以内に着手できる粒度)。例:「机に問題集とノートを開く」
  steps?: string[];           // AI生成の手順(任意)
  estimateMin: number;        // 見積時間(分)
  actualMin?: number;         // 実績時間(分)→ 効率計算に使う
  outcomePoints: 1 | 2 | 3 | 5; // 成果ポイント(小さな作業=1、重要な成果=5)
  deadline?: string;          // いつまでに(ISO日付)← カレンダー機能の中核
  scheduledDate?: string;     // いつやるか(deadlineから逆算して配置)
  scheduledTime?: string;     // 開始予定時刻(任意)
  bufferMin?: number;         // 移動・準備・休憩バッファ(AIが自動提案)
  status: 'inbox' | 'todo' | 'doing' | 'done' | 'dropped';
  tags: string[];             // 'study' | 'life' | 'creative' など
  subjectId?: string;         // 学習タスクの場合、科目への紐付け
  createdAt: string;
  completedAt?: string;
}

// 学習:科目と復習アイテム(間隔反復)
interface Subject {
  id: string;
  name: string;               // 数学、英語…
  weeklyTargetMin: number;    // 週あたり目標時間(配分の基準)
  weakPoints: string[];       // 「何を理解していないか」を明示的に貯める場所
}

interface ReviewItem {
  id: string;
  subjectId: string;
  content: string;            // 復習する内容(例:「三角関数の合成」)
  lastReviewedAt: string;
  intervalDays: number;       // 1 → 3 → 7 → 14 → 30 と伸ばす(簡易SM-2)
  nextReviewAt: string;       // この日が来たら自動で「今日」に復習タスクを生成
  confidence: 1 | 2 | 3;      // 復習時の手応え。低いと間隔をリセット
}

// Inbox:メモ・アイデア・決定事項・資料リンクの一元受け皿
interface InboxItem {
  id: string;
  text: string;
  kind?: 'memo' | 'idea' | 'decision' | 'resource' | 'task-candidate';
  createdAt: string;
  processedAt?: string;       // 夜のクローズで仕分けたら記録
  linkedTaskId?: string;
}

// 1日のプランとログ
interface DayPlan {
  date: string;
  topThree: string[];         // 今日の最重要タスク3つ(taskId)。優先順位はこれで固定
  firstTaskId: string;        // 「今日の最初の一手」= 前夜に確定しておくタスク
  recoveryCount: number;      // 復帰ボタンを押した回数(自己否定ではなく回数の記録として)
  review?: {
    didWell: string;
    stuck: string;
    tomorrowFirstStep: string; // 反省を「明日の行動」に強制変換する欄
    efficiencyScore: number;   // Σ成果ポイント ÷ Σ実績時間(時)
  };
}
```

## 4. 画面設計と「1日の使い方」

### 4.1 朝ランチャー(起床直後に開く画面)

**解決する困りごと:** 起きた瞬間に何をすべきか分からない/優先順位が分からない/決めるまでに時間が溶ける/スマホで流される

- 開くと**前夜に決めた「今日の最初の一手」だけが全画面で1つ表示**される。リストは見せない。
- ボタンは2つだけ:**[開始する]** と **[今日は無理そう → 縮小プラン]**。
- [開始する] を押すとタイマーが走り、今日ビューへ。
- 前夜に決め忘れていた場合のみ、AIが締切・昨日の実績から「今日のTop3+最初の一手」を10秒で提案する。
- **使い方のルール:** 朝、他のアプリより先にこれを開く(PWAとしてホーム画面に置く/朝の通知1本で起動導線を作る)。「考える」工程を前夜に終わらせてあるので、朝は選ばずに従うだけ。

### 4.2 今日ビュー(日中の主画面)

**解決する困りごと:** 短いタスクの後に次を迷う/休憩の取り方が分からない/何もしてない感

- 表示は3層のみ:
  1. **NOW** … 実行中タスク1つ(完了条件・残り見積時間つき)
  2. **NEXT** … 次の1つ(完了したら自動でNOWに繰り上がる → 迷う隙間を消す)
  3. **今日のTop3** の達成状況(チェック)
- タスク完了時に「実績時間」がタイマーから自動記録され、**成果ポイントが加算されるアニメーション**を出す(積み上がりの可視化)。
- 見積45分以上のタスクは自動で**25分作業+5分休憩**(ポモドーロ)に分割表示。休憩の取り方をアプリが決める。
- **使い方のルール:** タスクの追加はここでやらない(Inboxに投げる)。この画面は「実行専用」。

### 4.3 復帰モード(崩れたときの救済ルート)

**解決する困りごと:** 予定が崩れた瞬間に全部どうでもよくなる/失敗後の復帰ルートがない/YouTubeに流れる

- 今日ビューに常設の **[プランが崩れた]** ボタン。押すと:
  1. 未完了タスクと残り時間をAIに渡し、**「今からの縮小プラン」を1案だけ**返す(例:「Top3のうち②だけを20分縮小版でやる。①③は明日8時に自動再配置済み」)。
  2. 消化できなかったタスクは**自責メッセージなしで**翌日以降に自動再スケジュール。
  3. `recoveryCount` を+1して記録。「復帰した回数」はむしろ実績として夜の振り返りに表示する。
- 予定時刻を90分過ぎてもNOWが動いていない場合、アプリ側から「縮小プランに切り替える?」と通知(自動検知)。
- **使い方のルール:** 崩れたら考えずにこのボタンを押す。「今日は失敗」と判定する権限を自分から取り上げ、常に続きがある状態にする。

### 4.4 カレンダー/締切ビュー

**解決する困りごと:** いつまでにやればいいか分からない/移動・準備・休憩を入れ忘れる/書類・提出物の管理が散らばる

- タスクは **deadline(いつまで)** と **scheduledDate(いつやる)** を分離して持つ。
- 締切を入れると、AIが見積時間から**逆算して作業日を自動配置**(例:提出3日前に下書き、前日に見直し)。
- 外出・提出系のタスクには**準備/移動バッファをAIが自動提案**して前後に挿入(「持ち物確認 10分」ブロックを前夜に自動生成)。
- 週ビュー+「今後7日の締切」リストの2表示。月ビューは優先度低(MVP外)。
- 提出物・書類は `kind: 'resource'` のInboxItemとしてタスクに紐付け、「そのタスクを開けば必要書類に届く」状態にする。

### 4.5 学習モジュール

**解決する困りごと:** 何を理解していないか分からない/復習タイミングを忘れる/科目配分が分からない/「勉強した」の基準が曖昧
**方針:** 効率性 = 一定時間内の成果。時間ではなく成果ポイントで測る。

- **完了条件の定量化:** 学習タスクは「p.12–15を解いて丸付けまで」「英単語50個を2周」のように、AIが必ず数値つき完了条件に変換する。→「今日は勉強した」= 完了条件を満たした学習タスクが1つ以上ある、という明確な定義になる。
- **弱点リスト:** 問題を間違えたり詰まったりしたら、その場で `weakPoints` に1行追加(Inbox経由でもよい)。「何を理解していないか」がリストとして常に見える。
- **間隔反復(SRS):** 学習タスク完了時に「これは復習が必要?」と1タップで聞き、YESなら ReviewItem 化。1→3→7→14→30日の間隔で**復習タスクが自動で「今日」に湧く**。手応え(confidence)が低ければ間隔をリセット。
- **科目配分:** 各科目に週目標時間を設定し、実績との差分を棒グラフで表示。「どの科目をどれくらい」はこの差分を埋める形でAIが週次提案する。
- **効率スコア:** `Σ成果ポイント ÷ Σ実績時間` を日次・週次で表示。「長くやった日」ではなく「効率が良かった日」が上に来るランキングにする。

### 4.6 Inbox(情報の一元受け皿)

**解決する困りごと:** メモの場所を忘れる/情報が散らばる/アイデアが使える形にならない/決定事項が消える/調べ物中に目的を忘れる

- テキスト1行をとにかく放り込むだけの入力欄(ホーム画面ショートカット/共有メニューから直行)。
- 仕分けはその場でやらない。**夜のクローズ時にまとめて処理**し、AIが `task-candidate / idea / decision / resource` に自動分類+タスク候補には完了条件案まで付けて提示 → 人間は承認/修正するだけ。
- `decision`(決めたこと)は日付つきで「決定ログ」に積まれ、検索できる。
- 調べ物を始めるときは「何のために調べるか」をInboxに1行書いてから開始する運用(目的のリマインダーとして今日ビュー上部に固定表示)。

### 4.7 夜のクローズ画面

**解決する困りごと:** 振り返りをしないまま終わる/反省が行動に変換されない/明日の準備をしない/寝る準備が遅れる

- 就寝60〜90分前に通知で起動。**5分で終わる固定フロー**(長いと続かない):
  1. 今日の完了タスクと効率スコアを自動表示(入力不要、見るだけ)
  2. 「うまくいったこと」「詰まったこと」を各1行
  3. **「明日の最初の一手」を1つ選ぶ(必須・スキップ不可)** ← 朝ランチャーの燃料
  4. Inboxの未処理アイテムをAI分類案に沿って仕分け(1件2秒)
  5. 明日の持ち物・提出物チェックリスト(カレンダーから自動生成)を確認
- 完了すると「今日はクローズ済み」バッジ。**振り返り=書く作業ではなく、明日を予約する作業**と位置づける。

## 5. AI統合設計

### 5.1 どのAIを使うか(無料/低コスト)

前提:Claude ProやChatGPT Plusなどの**チャットサブスクはAPIには使えない**(サブスクとAPI課金は別)。
個人アプリに組み込むなら、無料枠のあるAPIを使うのが正解。

| 選択肢 | 無料枠 | 料金(超過時) | 評価 |
|---|---|---|---|
| **Google Gemini API(Flash系)** ★推奨 | あり。Flash系で目安 10リクエスト/分・1,500リクエスト/日(クレカ登録不要。ただしGoogleは予告なく枠を変更するので実際の値はAI Studioで確認) | 無料枠内なら0円 | このアプリの利用量(後述、1日10〜30回)なら**完全無料で運用可能** |
| Groq API(Llama等) | あり(無料枠) | 従量 | 高速。Geminiの代替・フォールバック先として |
| OpenRouter の free モデル | あり | — | 品質が不安定。実験用 |
| Anthropic Claude API(Haiku 4.5) | **無料枠なし** | $1/百万入力トークン・$5/百万出力トークン | 品質は高い。1回の呼び出し(入力1K+出力0.5Kトークン程度)で約0.5円 → 月数十円〜。無料にこだわらないなら有力 |

**推奨構成:** メイン = Gemini Flash(無料枠)、任意でフォールバック = ルールベース処理(AI不通時もアプリが止まらない)。
APIキーはユーザー自身が取得し、アプリの設定画面から入力して localStorage に保存(自分専用アプリなのでサーバ不要。公開アプリにするならキーを隠すための薄いプロキシを1枚挟む)。

### 5.2 AIの呼び出しポイントと使い方

| # | 機能 | 入力 | 出力(JSON固定) | 呼び出しタイミング | 回数/日 |
|---|---|---|---|---|---|
| 1 | **タスク分解・手順生成** | 「勉強する」「部屋を片付ける」等の生テキスト | `{title, doneCriteria, firstStep, steps[], estimateMin, outcomePoints, bufferMin}` | タスク登録時 | 3〜10 |
| 2 | **効率化手順の提案** | タスク+目的+持ち時間 | 「最短で成果を出す手順」を3〜5ステップで | タスク詳細で[効率化]ボタン | 0〜5 |
| 3 | **朝のプラン生成** | 締切一覧+昨日の実績+今日の可処分時間 | `{topThree[], firstTaskId, timeline[]}` | 前夜未設定時のみ | 0〜1 |
| 4 | **復帰プラン再構成** | 残タスク+残り時間 | 縮小プラン1案+再配置結果 | [プランが崩れた]押下時 | 0〜3 |
| 5 | **夜:Inbox自動分類** | 未処理InboxItem一式(1回にまとめて送る) | 各項目の `{kind, taskCandidate?}` | クローズ時に1回 | 1 |
| 6 | **夜:振り返り→行動変換** | 今日のログ+1行振り返り | 「明日の最初の一手」候補3つ | クローズ時に1回 | 1 |
| 7 | **週次:学習配分の見直し** | 科目別実績と目標、弱点リスト | 来週の科目別時間配分+重点弱点 | 週1回 | 週1 |

合計でも**1日10〜30リクエスト程度** → Gemini無料枠(目安1,500/日)の2%以下。無料で収まる。

### 5.3 プロンプト設計の要点

- 出力は**必ずJSONスキーマを指定**して構造化させ、アプリが直接取り込める形にする(自由文を返させない)。
- システムプロンプトに固定で入れるもの:
  - 「完了条件は必ず数値または観測可能な状態で書く」
  - 「最初の一手は2分以内に着手できる物理的動作にする」
  - 「効率性 = 一定時間内の成果。手順は成果に直結しない工程を削って提案する」
  - 「移動・準備・休憩バッファを必ず見積に含める」
- 失敗時(タイムアウト・枠切れ)は**ルールベースにフォールバック**:
  - タスク分解 → テンプレ(「〜を30分」+完了条件は手入力促し)
  - 復帰プラン → 「Top3の最上位だけを半分の時間で」固定ロジック
- 呼び出し削減:同じタスク文面の分解結果はローカルにキャッシュ。Inbox分類は1件ずつでなく夜に1回バッチ。

## 6. 実装順序(MVP → 拡張)

| フェーズ | 作るもの | それだけで解決する困りごと |
|---|---|---|
| **MVP(週1〜2)** | Task CRUD(完了条件必須)/今日ビュー(NOW+NEXT+Top3)/夜クローズ(明日の一手必須)/朝ランチャー | A(次の一手)・B(完了条件)・Dの一部 |
| **P2** | AI統合(分解①・朝プラン③・夜変換⑥)/Inbox+夜の一括分類⑤ | B強化・E(情報一元化) |
| **P3** | カレンダー(締切逆算・バッファ自動挿入)/復帰モード④ | C(復帰ルート)・スケジュール系 |
| **P4** | 学習モジュール(SRS・弱点リスト・効率スコア・週次配分⑦) | 勉強系すべて |
| **P5** | PWA化(通知・ホーム画面)/積み上げグラフ/決定ログ検索 | 習慣化・可視化 |

**注意:** 全部を最初に作らないこと。MVPの4画面だけでも「朝に迷わない・完了が分かる・夜に明日を予約する」のループは回り、それがこのアプリの核。

## 7. 技術メモ

- スタック:React + TypeScript + Vite(既存 daily-inquiry-log と同じ)。状態は localStorage 起点、量が増えたら IndexedDB。
- AI呼び出しは `fetch` で Gemini API を直叩き(`generateContent`、`responseMimeType: "application/json"` + `responseSchema` でJSON強制)。
- 通知は PWA + Notification API(朝の起動導線・夜のクローズ導線・崩れ検知の3本のみ。通知を増やすと無視される)。
- 効率スコア等の集計は全てクライアント側で計算(AI不要)。AIは「文章→構造化」と「プラン再構成」だけに使う。
